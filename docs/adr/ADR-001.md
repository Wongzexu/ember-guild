# ADR-001: 技术栈采用 Vue 3 + Vite 而非 Godot

> 日期：2026-08-26
> 状态：accepted
> 关联：DECISIONS.md「技术栈取舍」条目（2026-08-26）；`docs/research/godot-2026-status.md`；ADR-000（模板）

## 一、背景

规划期已暂定技术方案：**Vue 3 + Vite（JS 起步，后期可加 TS）**，无后端起步，M7 用 Electron 打包桌面小窗（见 ARCHITECTURE.md §2/§8）。M0 空壳已按此实现并验收通过。

2026-08-26 用户了解到 Godot 游戏引擎后，提出是否切换的评估需求。核心分歧点：Godot 提供**桌面原生导出**（免 Electron）与**动画/演出生态**（游戏引擎强项），但代价是重写已有 M0 代码、GDScript 重写引擎、放弃 Web 秒开体验。

派子代理按 research 流程调研了 Godot 4.7 现状（`docs/research/godot-2026-status.md`，8 项事实全带官方来源）。

## 二、决策

**技术栈维持 Vue 3 + Vite，不切换 Godot。** 桌面化照旧在 M7 走 Electron。

### 2.1 决策依据：开发便利性五维对比（本项目语境）

| 维度 | Vue 3 + Vite | Godot 4.7 |
|------|-------------|-----------|
| 热更新 | Vite HMR 毫秒级、保状态 | 无保状态 HMR，仅编辑器同步 |
| 测试 | Vitest（M0 已验证 6/6 绿） | 无官方框架，事实标准 GUT，生态弱 |
| Web 包体 | 几百 KB 秒开 | wasm 空项目 25-33MB（压缩 ~6MB） |
| 密集数据 UI（背包/词缀/图鉴/悬浮提示） | HTML/CSS + 响应式，天然擅长 | Control 节点可做，数百格需自研虚拟滚动 |
| 存量代码 | M0 引擎 + 面板直接复用 | 引擎需用 GDScript 重写（非 1:1 复制） |

Godot 的优势（原生小窗、动画/粒子/演出）均属于本项目**最不急的层**：战斗为自动对撞（演出薄），桌面化在 M7 才需要。

### 2.2 决策依据：调研事实补充

- Godot 4.7.2 为当前稳定版，无 LTS 品牌、滚动支持；
- 2D/挂机类游戏在 Godot 可行（有 Melvor Idle 风格教程先例），但密集 UI 与 Web 加载体验差距明显；
- 中文社区活跃，非决策障碍。

## 三、后果

### 正面影响
- 迭代速度与测试体验保持 Web 生态最优（本项目核心诉求：数字驱动、数据密集 UI）；
- M0 资产零浪费，M1 可直接继续；
- 网页形态轻量，未来若想"打开链接即玩"仍保留通道。

### 代价与风险
- M7 桌面化需处理 Electron（包体较大、内存占用高于原生）；
- 动画/战斗演出需自行实现或引入 Web 动画方案（如 Canvas/GSAP），无引擎级工具；
- 若未来游戏转向重度演出/动作化，需重新评估（后悔条件明确）。

## 四、排除事项

- **不在任何里程碑混用 Godot 做部分模块**（引擎层保持单一技术栈）；
- **不因单一因素（如"引擎更专业"）重开引擎切换评估**——除非出现可量化的强信号（如：Web 无法满足的演出/性能需求、Electron 桌面化遇到不可解问题）；
- 不采用 Godot 的 Web 导出作为桌面替代路径。

## 五、实施与验证

1. M0 已按 Vue 3 + Vite 实现并验收（2026-08-26，M0-BLUEPRINT 5/5）；
2. 后续里程碑（M1~M7）全部在 Vue 技术栈内开发；
3. 验证方式：M7 以"同一份代码 Electron 打包、双击即玩"为最终验收；若届时桌面体验（包体/内存/小窗形态）不可接受，触发后悔条件重开评估（见排除事项）。
